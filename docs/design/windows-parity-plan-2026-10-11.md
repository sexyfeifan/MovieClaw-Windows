# MovieClaw Windows 对齐 macOS 的代码审计和实施计划

Windows 0.2.111 已具备本地界面、原生播放和部分播放器交互，但核心功能存在服务端合同错配，播放状态与生命周期也未闭合。继续开发应先恢复搜索、账号、续播、换画质和退出等完整用户路径，再统一页面与交互，最后用 Windows 真机与 macOS 同条件验收性能。保留 Tauri、WebView2 和 mpv 架构，按模块补齐即可；当前证据不支持为此重写整个客户端。

## 对齐基线和范围

审计日期为北京时间 2026 年 10 月 11 日。Windows 基线是 `desktop-v0.2.111`，提交 `30cd3642daba58f2cc3e614b269c335c108beb59`，分支 `feat/windows-native`。该提交与拉取后的 HEAD 一致。[发布页](https://github.com/sexyfeifan/MovieClaw-Windows/releases/tag/desktop-v0.2.111)

macOS 基线取上游最新 `main` 的固定提交 `9139a638a391ed91bcb2d48940b6e8d595de5a56`，实际界面入口是 `apps/apple/MovieClawMac`，共用逻辑在 `Shared` 与 `AetherCore`。本地 Windows 仓库内嵌的 Apple 源码落后于这一基线，因此只照本仓旧文档补齐会漏掉长季分段、服务端续播锚点和播放时置顶等新功能。[上游基线](https://github.com/yipengfei329/movieclaw/tree/9139a638a391ed91bcb2d48940b6e8d595de5a56/apps/apple/MovieClawMac)

“一样”落实为三份可验收的合同：

| 目标 | 验收口径 |
| --- | --- |
| 一样的界面 | 同一账号和数据下，页面层级、布局、内容、状态、操作入口和动效一致；字体栅格化、系统窗口按钮与系统材质按平台处理 |
| 一样的功能 | macOS 实际开放的全部用户路径，Windows 均有可用入口、正确请求、正确结果和异常恢复 |
| 一样的性能 | 同一服务器、文件、网络和输出条件下比较首帧、seek、滚动、输入、卡顿与资源；不同硬件的 CPU 百分比不能直接互比 |

范围包括欢迎与登录、多账号、首页、收藏、媒体库、合集、搜索、详情、人物作品和播放。macOS 当前未开放的发现、订阅、Reels、活动、AI 和库管理页不属于这一轮 macOS 对齐目标。Windows 现有播放设置保留并修成真正生效的设置。类型货架等功能只按基线实际可见行为对齐，不能从 iOS 或设计稿推断 macOS 已经拥有。

本次完成的是代码审计、合同探针和计划，没有修改应用源代码或发布新版本。Windows GPU、HDR、音频输出、WebView2 与窗口合成仍需在 Windows 真机验收，下面的代码复现不能代替这些实机结果。

## 已经完成的能力

这些能力有现成实现，后续以回归验证和补齐边界为主：

- 本地 `desktop/index.html` 页面与自绘窗口外壳；当前实现已经不是 README 所写的加载服务端 Web UI 再注入播放桥。
- 检出 mpv 时按原生能力协商原文件直出；mpv 启动失败后改报浏览器能力重新协商。
- mpv JSON IPC 的暂停、seek、音量控制，以及播放区域随窗口尺寸变化。
- 共享 HTTP 连接池和详情页预连，减少起播阶段的串行请求。
- 双行玻璃控制条、上下集按钮、剩余与总长切换、Esc 阶梯和拖动跟随策略。
- 掉帧与卡顿判定、网络重连入口、画质建议、错误重试和软件转码同意弹窗。
- 详情页头图、文件版本、人物卡和系列展示的主要结构。

已下载并只检查 0.2.111 便携包目录，确认包含 `mpv/mpv.exe`、`WebView2Loader.dll` 和桌面 UI；ZIP SHA256 为 `2425bcb7c8373d0e274308941e0605a79244bbdb03a5da08a27435ad98396cfd`，与发布页一致。后面的打包问题是仓库流程不能可靠复现已发包，不能据此说当前发布包没有 mpv。

## 旧差距清单需要修正的内容

`docs/design/windows-parity.md` 有参考价值，但不能直接当完成记录：

- mpv 的 `sessionId` 已在 `app.js:2184` 设置。真正缺口是上报启动、最终位置、EOF 和生命周期，不能重复补一个已存在的赋值。
- 原文件直出 tier 0 的 `session_id=null` 是服务端明确的无会话设计，不需要人为制造 sessionId；转码等有会话路径才要 ping 和 DELETE。
- HTML5 换画质的 capability 位置已修正，剩下的是季集、时间轴、会话替换和错误路径。
- Mac 首页已经关闭慢推近 `animatesZoom:false`；不能把旧的 40 秒首页慢推镜当成必须新增的效果。
- “Windows 已有我的媒体库卡”和“已有扫码登录”不准确；最近添加货架不等于 Mac 库卡，文字码加错误接口不等于可用 QR 登录。
- Mac 实际可见 UI 未核实到 removeAccount 入口；Windows 的移除账号可作为账户管理完善项，不应称为已确认的 Mac 缺失功能。
- 新上游增加长季分段、全部分集宫格、服务端续播锚点和播放时置顶，需要纳入新基线。
- 文档曾记载的起播耗时和真机测试属于历史记录，本次未复跑，不能作为 0.2.111 已通过的性能结论。

## 后续架构

保持本地 UI，按以下边界逐步整理。拆分随缺陷修复进行，避免同时改掉全部页面。

| 边界 | 职责 | 实施原则 |
| --- | --- | --- |
| API 合同层 | 显式解析搜索、账户、人物、首页、会话和错误结构；保留分页与响应头 | 优先用准确 DTO 和适配函数替换通用 unwrap，契约来自同一版 OpenAPI |
| ServerContext 和 AccountStore | server、用户、凭证、能力、缓存键与上下文代数 | 切换账号或服务器时原子替换；作废在途请求、播放和旧界面数据 |
| Router 和页面 Store | 每入口独立导航栈、缓存、分页、刷新、请求取消 | 页面不会被旧响应覆盖；返回时恢复滚动与搜索 |
| PlaybackController | 会话、文件时间轴、进度、重试预算、换画质、换集和关闭 | 只有一条协商与替换链，HTML5 与 mpv 共享同一语义 |
| PlayerBackend | load、pause、seek、volume、speed、音轨、字幕、观测、EOF 和错误 | MpvBackend 与 Html5Backend 有同一事件合同；UI 不再直接操作隐藏 video |
| 平台服务 | 窗口、HDR与音频能力、SMTC、休眠抑制、发现、凭证和升级 | 可独立真机验证，关闭后释放资源 |

macOS 的 `PlaybackController`、FailurePolicy、ScrubFollow 和质量记忆提供行为规范与测试向量，Windows 无需采用 Apple 引擎。原生播放以 mpv 为主，HTML5/HLS 保留受支持的转码与回退路径。原盘和特殊格式进入原生路径前先核实所带 mpv 构建能力，失败必须有可解释的降级。[mpv 命令与属性规范](https://mpv.io/manual/stable/)

## 分阶段实施

### 阶段零 固定基线和建立可复现验证

这是后续所有阶段的起点，打包修复可以与核心合同修复并行。

1. 固定 Windows 与 Mac SHA，建立逐页截图和行为清单；以最新 Mac 实际界面校正旧 parity 表。
2. 在 Windows 设置可运行的 Debug/Release 测试环境，并保存 0.2.111 的基线数据。记录 OS、GPU/驱动、显示器 HDR 与缩放、WebView2、mpv、服务器版本。
3. 修正三个打包入口，统一调用同一个组装脚本，固定 Rust target 与 mpv 来源、版本、哈希；必要文件缺失立即失败。
4. 版本号从单一来源生成 Rust、Tauri、NSIS、包名和关于页；清理旧注入式 README。
5. Desktop CI 覆盖实际开发分支与 PR，使用锁文件，加入客户端合同测试、Windows 构建和安装烟测，不能只有名为 Build & Test 的构建任务。

验收：全新 Windows 用户无需开发机路径或另设 MOVIECLAW_MPV 即可安装并播放；安装包与便携包具备一致的 mpv、UI、运行依赖和第三方许可证清单；关于页版本等于包版本。验证无 WebView2 环境下明确提示或引导安装，不能把 Loader DLL 当运行时本体。

交付：可复现构建、固定版本的测试素材清单、首份 Windows 性能基线、逐页对齐表。

### 阶段一 修通核心合同和浏览正确性

对应 F01–F07、F19。先修正确结果，再扩大界面。

1. 搜索显式展开 hit.item，保留 library_ids 与 match，正确跳到所属库；人物页读 PersonView.credits，处理角色与导演分类。
2. 先修现有 Cookie 账号合同为 username/active；修添加账号入口，不能只是返回服务器连接页；登录页从窗口事件绑定中独立出来。
3. 拆分网络失败、401、未初始化和版本不兼容状态；错误保留结构化 status/detail，登录恢复后回到原路由。
4. 墙改为按服务端分页获取，一页到达即展示，按 source 和 generation 去重；移除 200 项截断和 5100 项静默上限。
5. 排序、方向、未看过滤走服务端；按 server 和 user 和 library 保存偏好。实际使用的首页、收藏、合集和搜索分页均接通。
6. 页面请求统一代数守卫和取消；重复登录不叠加全局监听。旧请求结束不能重建新页面。
7. up-next 使用 data.items；继续第几季以服务端真实状态为准。
8. 将媒体文字、查询词与错误消息通过textContent和安全属性赋值写入；模板必须有统一转义。按实际worker、图片与流来源制定CSP和最小Tauri权限；用含引号、尖括号及中文的真实文本验收显示和不执行事件。

验收：合法电影、剧集、别名和人物搜索均可进入正确详情；两个不同账号可切换；人物作品非空；10 万项库也不先全量加载，首屏一页即可呈现，滚到底无丢项和重复；快速 A→B 搜索、电影库→剧集库不被迟到 A 覆盖；未登录窗口按钮可用。

交付：核心浏览与账号 Cookie 路径可用的修复版本，以及对应接口合同和用户路径回归。

### 阶段二 统一播放状态和会话生命周期

对应 F08–F13，并修 F20 的 Range 和取消语义。它是轨道、异常恢复和性能工作的前置。

1. 明确 PlaybackContext：server、account、library、media、season、episode、attempt、session、backend、generation。启动、换画质和换集都经过同一替换流程。
2. 文件时间与引擎时间只有一处换算：session 流的文件时间为 originMs 加引擎时间；file 流直接用引擎时间。显式 0 与未指定起点区分，时长优先取源文件真实时长。
3. mpv 首帧后启动 start/progress；有会话才 ping；退出先保存最后有效状态，再停引擎、完成 stop 和 DELETE。退出 App 有有界收尾，失败请求进入有限队列。
4. 统一 EOF、进程退出、网络中断和内容失败；保留最后有效 position/duration；异常提前结束不能当正常看完。
5. 替换会话时释放旧会话；迟到但已经创建的会话也必须回收，不能只丢弃响应。切画质继续同一观看 attempt 并保留季集和所有记忆。
6. 自动下一集与控制条下一集共用一个动作，保留 library_id；关闭、换片、换账号时清倒计时与所有监听。
7. 补 Range、206、超时与真正取消；所有 HLS 创建路径共用 ERROR 处理、重试与清理逻辑。
8. stop 上报成功后发布本地刷新事件，详情、分集、收藏和首页立刻更新。

测试固定同一NAS、相同文件ID、编码/码率、音轨与字幕、窗口/分辨率与刷新率。冷缓存和暖缓存分开，网络条件按LAN、外网、600KB/s慢链、延迟/丢包和短断网分组；多构建交替测试，每组至少30次起播/seek，发布P50/P95和失败数。

资源不能要求Windows机器的CPU百分比等于Apple Silicon。Windows端另用同一台机器上的独立mpv作播放开销参考，统计整个客户端进程树的CPU、GPU、内存与实际硬解。Mac历史性能文档本身也有未达标项，因此既比较体验，也保留共同最低门槛。

性能修改顺序：先减少大库全量请求和DOM、建立图片尺寸与缓存；再把大二进制从base64/JSON改为受控且可取消的二进制流，保留Range和必要响应头；再优化mpv观测的轮询/事件、缓冲和seek。Mac的matroska_cues与跨启动缓存优化只能参考其目标，先测Windows的瓶颈，再决定是否需要自有索引/缓存，避免未测量就搭一个新引擎。

QoE至少记录attempt、后端、协商/首帧分段、卡顿原因、seek延迟、重连/换质、最后结果和上报投递事实；解析Server-Timing并接现有metrics/client-log接口。日志去掉Cookie、Token、密码和带签名取流URL。

交付：媒体能力表、Windows/Mac对照数据、可复跑的性能报告与剩余风险。

## 执行顺序和并行安排

第一批应交付合同修复、分页与请求守卫，同时修构建与打包。第二批集中统一播放时间轴、会话与退出。第三批完成真实轨道控制和错误恢复，并与服务端windows设备支持、凭证迁移并行。第四批完成全部页面和平台交互；最后集中做跨GPU媒体覆盖、性能优化和发布验收。

依赖关系是：固定测试环境 → API/上下文正确 → 播放生命周期正确 → 原生控制与可靠性 → 完整UI → 媒体与性能验收 → 发布。页面视觉可以在合同修复后并行，但性能结论必须在生命周期与资源释放修复后产生。每批使用小范围PR/提交，带用户路径回归，阶段未通过时不把对应项目记为完成。

当前已确认修复面远超过一次样式迭代。工期需要在Windows基线建立后按HDR/原盘兼容结果估计；用户路径与性能验收决定完成时间，而非预先承诺某个版本号就全部对等。
